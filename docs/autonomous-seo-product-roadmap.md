## Decision log

### Complete secure password and passphrase generation

- **Evidence:** `/tools/password-generator` used `randomUint32 % poolLength`, which gives some characters a slightly higher probability whenever the pool does not divide 2^32. Selecting a character-class checkbox only expanded the pool and did not guarantee that class appeared. The page also labelled a simple pool-size estimate as “strength,” generated only one value and lacked passphrases, exclusions, export and substantive security guidance.
- **Decision:** Keep one canonical generator for both manager-friendly random strings and readable generated passphrases. Use Web Crypto rejection sampling at both the 32-bit index and whole-password constraint levels, making the distribution uniform over strings that satisfy every enabled class. Present mathematical entropy as a randomness estimate, not an account-security verdict.
- **Change:** Add 8–128 character and 1–50 item controls, guaranteed uppercase/lowercase/number/symbol classes, ambiguous-character and custom exclusions, quick presets, 4–12 independently selected compound passphrases, separators/capitalization/two-digit suffix, reveal/hide, per-value and batch copy, plaintext download and reset. Compute entropy from the exact count of class-valid strings or the documented 256-compound space. Add unique metadata/H1, WebApplication data, breadcrumb, unbiased-generation explanation, password/passphrase comparison, device/clipboard/export limits, password-manager and MFA guidance, FAQ and related tools.
- **Validation:** `npm run lint`, `npm run build`, deterministic rejection above the unbiased range, invalid options, guaranteed classes, exclusions, ambiguity filtering, exact entropy counts, passphrase composition/suffix and batch cases, plus prerendered metadata/JSON-LD/content inspection.
- **Implementing commit:** This commit — `feat: complete secure password generator`.
- **Remaining gap:** The compact 256-compound vocabulary is transparent and testable but is not a recovery-seed or natural-language word list. Site-specific password rules still need the user to choose compatible settings.
- **Next recommended increment:** Complete URL encoding (P14), separating whole URL, path component, query value and form-encoding semantics instead of encoding every input as one component.

### Complete JWT inspection and trust workflow

- **Evidence:** `/tools/jwt-decoder` was an adjacent security utility with no supplied query signal, but it accepted permissive Base64 and non-object JSON, treated any decodable token as “Valid,” checked only `exp`, and placed its signature warning beneath the output. That could confuse readable attacker-controlled claims with authentication.
- **Decision:** Complete the existing canonical page as a strict inspector, not an in-browser verifier. Verification depends on a trusted key, an application-selected algorithm, issuer, audience, clock tolerance and policy, so adding a key field would create a misleading generic trust decision and encourage secret handling in the browser.
- **Change:** Require exactly three compact, whitespace-free, canonical unpadded Base64URL segments; fatal UTF-8; object-valued header/payload JSON; a non-empty `alg`; and a structurally valid signature, with the deliberate unsigned `alg: none` exception. Add deterministic `exp`, `nbf` and `iat` NumericDate inspection, invalid/future/expired states, algorithm and critical-header warnings, sample/paste/local upload/clear/reset, section copy, signing-input copy and a downloadable inspection report. Replace “Valid” with explicit “Decodable” and “Not verified” states, plus security-first metadata/H1, steps, trust guidance, privacy, FAQ, structured data, breadcrumb and related tools.
- **Validation:** `npm run lint`, `npm run build`, deterministic valid/expired/not-before/future-issued/invalid time, wrong segment count, whitespace, non-canonical Base64URL, invalid UTF-8/JSON/object/algorithm/signature and `alg: none` cases, plus prerendered metadata/JSON-LD/content inspection.
- **Implementing commit:** This commit — `feat: complete JWT inspection workflow`.
- **Remaining gap:** The page intentionally does not decrypt five-part JWE values or verify signatures. Those operations require trusted server-side key and policy context; the inspector cannot safely infer them from the token itself.
- **Next recommended increment:** Completed by the password generation decision above; move to the URL component and query encoding workflow (P14).
